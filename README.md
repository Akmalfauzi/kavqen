# KavQen — Voice Agent Form Filler Monorepo

General-purpose voice agent that converts natural audio conversations into structured form fields in real-time. Built on top of **AssemblyAI Voice Agent API**.

## Monorepo Architecture

- **`apps/client`**: Next.js 14+ (App Router) Frontend for live split-screen voice & form filler UI.
- **`apps/gateway`**: Node.js + Express + Socket.IO + AssemblyAI WebSocket Bridge Server.
- **`apps/ai-service`**: Python 3.12 + FastAPI AI & Business logic engine (Prompt builder, JSON Schema engine, Field validator).
- **`configs/`**: Shared JSON form configurations (e.g. `clinic.json`, `complaint.json`).

## Setup & Running

### Prerequisites
- Node.js >= 18.0.0
- Python >= 3.11
- pnpm / npm

### Setup

1. **Install JS/TS dependencies:**
   ```bash
   pnpm install
   # or
   npm install
   ```

2. **Setup Python AI Service:**
   ```bash
   cd apps/ai-service
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```

### Running Services

- **Run Client Frontend:** `pnpm --filter client dev` (http://localhost:3002)
- **Run Gateway Server:** `pnpm --filter gateway dev` (http://localhost:3003)
- **Run AI Service:** `cd apps/ai-service && uvicorn main:app --reload --port 8001` (http://localhost:8001)

## Local demo: owner shares a form

Run database migrations and the repeatable demo seed:

```bash
pnpm --filter gateway exec prisma migrate deploy
pnpm --filter gateway exec tsx prisma/seed.ts
```

- Owner: `owner@demo.kavqen.test` / `KavqenDemo2026!`
- Participant: `participant@demo.kavqen.test` / `KavqenDemo2026!`
- Three fixed agents: Merchant Onboarding, Clinic Appointment Request, Customer Support Request.
- Three published workflows/forms and 34 fictional submissions (enough for pagination).
- Share codes: `KQ-DEMO-MERCHANT`, `KQ-DEMO-CLINIC`, `KQ-DEMO-SUPPORT`, valid for 30 days after seeding.

Public signup (email or verified Google identity) always assigns the server-selected Participant role. There is no owner role selector. New participants receive invitations to the three demo forms; accept an invitation on the dashboard before filling a form. The owner can also share time-limited codes or invite a specific email. Role and ownership are read from the database, not trusted from request payloads. Adding/deleting agents and workflows is blocked by the API, including for the owner. Owners may edit and republish their existing workflows.

Seeding is repeatable. It retires old agents/workflows from the active catalog without deleting historical submissions. It creates or refreshes the demo accounts and sample submissions. It does not reset real participant submissions. Use a demo database for this seed.

Knowledge uses Qdrant vector search with local FastEmbed `BAAI/bge-small-en-v1.5` embeddings, not pgvector. PostgreSQL retains document content, ownership, and revision checks. Document create/update/delete synchronizes Qdrant; retrieval always filters by authenticated owner, then verifies current DB ownership, deletion status, and content revision. Search and new voice sessions retrieve fresh knowledge; an existing call needs restarting after edits.

## Running with Docker

### Manually restore the demo

**Destructive:** this removes all accounts, submissions, invitations, integrations,
and other records in the configured database, clears the configured Kavqen Qdrant
collection, applies migrations, then restores the demo seed. Back up the database
first. Stop client/gateway traffic and keep AI service plus Qdrant running.
Check `DATABASE_URL` in `apps/gateway/.env` before executing.

```bash
# Local app services:
pnpm demo:reset

# Docker app services (AI service must already be running):
pnpm demo:reset docker
```

The script requires typing `RESET KAVQEN DEMO`. It does not clear browser
localStorage; sign out and sign in again after resetting. Published demo workflow
JSON files are regenerated by the seed. Unrelated files in `configs` are preserved.

### Start the stack

The root `Dockerfile` contains production targets for the client, gateway, and AI service. Docker Compose builds the three application services and starts Qdrant with persistent storage. The embedding model is downloaded while building the AI image; calls do not need an external embedding API key.

1. Configure gateway settings in `apps/gateway/.env` (copy `.env.example` only if the file does not exist). Set `ASSEMBLYAI_API_KEY`, `DATABASE_URL`, `JWT_SECRET`, Google credentials, and SMTP credentials. For PostgreSQL running on the host, use `host.docker.internal` instead of `localhost` in `DATABASE_URL`. Compose does not create a database server.

2. Generate `KNOWLEDGE_INTERNAL_TOKEN` with `openssl rand -hex 32` and set it in root `.env`. Compose passes it to both gateway and AI service. Copy `.env.docker.example` to `.env` if needed. Set `NEXT_PUBLIC_GOOGLE_CLIENT_ID` to the same value as gateway `GOOGLE_CLIENT_ID`. Keep `NEXT_PUBLIC_ENCRYPTION_KEY` consistent with gateway `ENCRYPTION_KEY`. On a remote server, replace the public URLs with HTTPS origins. Google must allow the client origin and Calendar callback URL.

3. Build the images and apply database migrations:
   ```bash
   docker compose build
   docker compose up -d qdrant ai-service
   docker compose run --rm --no-deps gateway node node_modules/prisma/build/index.js migrate deploy
   ```
   For a fresh database, initialize the default roles and demo data when needed:
   ```bash
   docker compose run --rm --no-deps gateway node --import tsx prisma/seed.ts
   ```

4. Start services and check logs:
   ```bash
   docker compose up -d
   docker compose ps
   docker compose logs -f
   ```

The client is available at http://localhost:3002 and gateway at http://localhost:3003. The AI service stays private inside the Docker network on port `8001`. Stop local development servers using these ports before starting Docker.

HTTP API calls use the client's `/gateway` proxy, which forwards to `gateway:3003` inside Docker. Socket.IO uses `NEXT_PUBLIC_SOCKET_URL`. Client build output is `.next-build`, separate from the development `.next` directory. Rebuild the client after changing `NEXT_PUBLIC_*` variables.

Stop the stack with `docker compose down`. Workflow JSON files are bind-mounted from `./configs`, so edits persist on the host. Database records remain in the PostgreSQL instance configured by `DATABASE_URL`.

To index existing knowledge documents after upgrading:
```bash
docker compose run --rm --no-deps gateway node --import tsx prisma/seed-knowledge.ts
```
For local development without Docker application containers, run Qdrant on localhost:6333 and install the AI service requirements. Set matching `KNOWLEDGE_INTERNAL_TOKEN` values in `apps/gateway/.env` and `apps/ai-service/.env`; see their examples. Docker Qdrant is bound only to `127.0.0.1:6333` for local development, not public network interfaces.
